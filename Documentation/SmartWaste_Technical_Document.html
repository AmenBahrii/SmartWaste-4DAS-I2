CHAPTER 01

Executive overview

SmartWaste is a centralized smart-city waste and recycling management platform connecting citizens, garbage trucks, smart recycling bins and city administrators. Its central objective is to close the information gap between what happens in the street, what citizens report and what collection teams know.

The presentation identifies three operational problems: fixed collection schedules do not reflect real bin fill levels; citizen reporting is slow and scattered; and the absence of timely feedback weakens incident response and recycling participation.

The proposed response is a five-service platform organized around monitoring, planning, citizen engagement and notifications.

Expected benefits

  • Cleaner public spaces
  • Fewer unnecessary collection trips
  • Better recycling participation
  • Faster incident resolution
  • Better use of city resources
CHAPTER 02

Problem, objectives and scope

Problem statement

  • Trucks may visit half-empty bins while full bins wait because collection follows fixed schedules rather than current demand.
  • Citizens lack a simple way to report a full or broken bin; reports can remain unresolved for days.
  • Teams are not warned in time, and recycling contributions are not rewarded promptly.

Project objectives

  1. Monitor bin fill levels and locations.
  2. Use current bin information to support collection planning.
  3. Allow citizens to submit incident reports with a photo.
  4. Track report status through resolution or rejection.
  5. Notify the appropriate role when important events occur.
  6. Support eco-points and rewards to encourage participation.

Actors and scope

CHAPTER 06

Inter-service communication

The platform uses two communication modes. Synchronous REST/OpenFeign calls are used when a caller needs an immediate answer. Asynchronous RabbitMQ events are used to announce completed actions without making the publisher wait for consumers.

#From → ToModePurpose / payload
1MS4 → MS1Synchronous · OpenFeignGET /api/users/{id} validates that the reporting user exists before a report is accepted.
2MS4 → MS2Synchronous · OpenFeignGET /api/bins/{id} validates that the referenced bin exists.
3MS3 → MS2Synchronous · OpenFeignGET /api/bins/{id} retrieves bin coordinates and capacity for route planning.
4MS2 → MS3 and MS5Asynchronous · RabbitMQBinFullEvent announces binId, location and fill level when the threshold is reached.
5MS4 → MS5Asynchronous · RabbitMQIncidentReportedEvent announces a new report using report/incident ID, bin, title and date.

Additional event flows defined in service-specific slides

  • MS3 publishes RouteCompletedEvent. MS2 consumes it and resets the fill level of collected bins.
  • MS4 is described as publishing IncidentResolvedEvent when a report is resolved. MS1 consumes it, creates RewardHistory and increments pointsBalance.
  • MS5 consumes BinFullEvent and IncidentReportedEvent.

Reliability behavior described

  • For MS4 validation calls, a timeout/fallback may allow the report to be saved as PENDING when MS1 or MS2 is unavailable; retry is described for later.
  • For MS3, if MS1 or MS2 is down, timeout and circuit breaker behavior is described; new route creation is refused with HTTP 503, while saved routes retain stored coordinates.
  • If the external routing API is down, MS3 uses a straight-line estimate and marks estimated=true.
  • If RabbitMQ is down, the presentation says events are retried or wait in the queue. If MS5 is down, its queued event waits until the consumer restarts.
Documentation note
The deck does not specify exact retry intervals, retry limits, dead-letter routing policy beyond the MS5 DLX name, timeout durations or circuit-breaker thresholds.
CHAPTER 07

Security model

The presentation defines a login-once flow based on Keycloak-issued JWTs and API Gateway validation.

  1. The user signs in through Keycloak from the web or mobile application.
  2. Keycloak returns a signed JWT containing the user's role.
  3. The client sends API requests to the API Gateway with the JWT.
  4. The gateway verifies the token signature using Keycloak's public keys.
  5. If valid, the gateway forwards the request to the target microservice.
RuleExpected behavior
Missing or invalid token401 Unauthorized.
Authenticated user with insufficient role403 Forbidden.
Public exposureOnly the API Gateway is public; microservices remain on the private network.
Role examplesCITIZEN, DRIVER and ADMINISTRATOR are the platform actors; some service contracts use OPERATOR as a recipient role.
Documentation note
The presentation does not define token lifetimes, refresh-token policy, password policy, fine-grained authorization matrix, CORS policy, secrets management or encryption-at-rest configuration.
CHAPTER 08

MS1 — Identity & Rewards

MS1 manages registration, login, user profiles, roles, eco-points and reward history. It owns User and RewardHistory.

Work plan

  1. Create the User and RewardHistory data model.
  2. Implement registration, login and role handling.
  3. Implement profile and reward-history endpoints.
  4. Consume IncidentResolvedEvent and award points.
  5. Add unit tests and document the API contract.

Relationships and integration

A User has zero or more RewardHistory entries. Other services store a plain userId rather than a foreign key. MS4 calls MS1 synchronously to validate a userId. MS1 consumes IncidentResolvedEvent from MS4 to award eco-points.

CHAPTER 10

MS3 — Fleet & Routing

MS3 manages garbage trucks, daily pickup routes, ordered route stops and collection progress. Administrators plan routes; drivers follow assigned routes and mark stops as collected.

Service profile

PropertyValue
Spring Boot port8083
Eureka service nameFLEET-ROUTING-SERVICE
DatabasePostgreSQL (fleet_db)
Gateway routes/api/trucks and /api/routes

Core workflows

  1. Manage trucks using plate number, capacity and status (AVAILABLE, ON_ROUTE or MAINTENANCE).
  2. Plan a daily route using a truck, a driver, a date and an ordered list of bins; obtain distance information from a routing API.
  3. Track collection by marking individual stops as COLLECTED. When the route is completed, publish RouteCompletedEvent so MS2 can reset collected-bin fill levels.

Data model

EntityAttributes
Truckid: Long; plateNumber: String; capacityKg: double; status: TruckStatus.
Routeid: Long; date: LocalDate; status: RouteStatus; truckId: Long; driverId: String; totalDistanceKm: double; durationMin: int; estimated: boolean.
RouteStopid: Long; routeId: Long; binId: String; latitude: double; longitude: double; sequenceOrder: int; status: StopStatus; collectedAt: LocalDateTime.

Relationship constraints shown: one Truck can be associated with zero or more Routes; one Route contains one or more RouteStops. The slide notes that relational transactions prevent a truck from having two routes on one day.

Service layers and clients

  • RouteController exposes the REST API.
  • RouteService contains business rules.
  • RouteRepository persists route data in PostgreSQL.
  • BinClient uses OpenFeign to call MS2.
  • UserClient uses OpenFeign to call MS1.
  • RoutingApiClient calls an external routing API over REST.
  • RouteEventPublisher publishes events through RabbitMQ.

Interactions and failure behavior

  • MS3 calls MS1 with GET /api/users/{id} to check the driver.
  • MS3 calls MS2 with GET /api/bins/{id} to obtain bin coordinates.
  • The routing API provides distance and duration.
  • If MS1 or MS2 is unavailable, the described timeout/circuit-breaker path refuses route creation with 503; previously saved routes retain stored coordinates.
  • If the routing API is unavailable, a straight-line estimate is used and estimated=true is stored.
  • MS3 publishes RouteCompletedEvent to exchange smartwaste.events; MS2 consumes it and resets collected bins.

One report is stored as one MongoDB document. The report stores userId and binId as identifiers only; it does not create cross-service foreign keys or duplicate the full user/bin records.

Internal layers

  • IncidentController exposes the REST API.
  • IncidentService contains business rules.
  • IncidentRepository persists documents in MongoDB.
  • BinClient validates bins through OpenFeign to MS2.
  • IncidentEventPublisher publishes RabbitMQ events.

Interactions and resilience

  • MS4 is called through the API Gateway at /api/incidents.
  • Before accepting a report, MS4 calls MS2 GET /api/bins/{id} and MS1 GET /api/users/{id}.
  • MS4 publishes IncidentReportedEvent so MS5 can notify administrators.
  • If MS1 or MS2 is unavailable, timeout/circuit-breaker behavior is described; the report may be saved as PENDING and the check retried later.
  • If RabbitMQ is unavailable, the report is still saved and event publication is retried. If MS5 is unavailable, the event waits in the queue until MS5 restarts.

Event processing

  • MS2 publishes BinFullEvent when fillLevel ≥ 90%; the event key is bin.full.
  • MS4 publishes IncidentReportedEvent; the event key is incident.reported.
  • RabbitMQ exchange: smartwaste.events (topic).
  • Durable queues: alerts.bin-full and alerts.incident-reported.
  • Dead-letter exchange: smartwaste.events.dlx for poison messages.
  • MS5 checks eventId for idempotency before creating an alert.
  • A critical bin-full alert targets DRIVER; a warning incident-reported alert targets OPERATOR.

CHAPTER 13

End-to-end business workflows

A. Bin reaches the critical fill level

  1. A bin's fill level is updated in MS2.
  2. When the threshold is reached (≥ 90% in the MS5 design), MS2 publishes BinFullEvent.
  3. RabbitMQ routes the event to the fleet/routing and alerts consumers.
  4. MS5 checks eventId to prevent duplicate alert creation and creates a CRITICAL alert targeted at DRIVER.
  5. MS3 can use the bin data to support pickup planning.

B. Citizen submits an incident

  1. Citizen submits title, description, photo and the concerned bin through MS4.
  2. MS4 validates the user with MS1 and the bin with MS2 using synchronous OpenFeign calls.
  3. MS4 stores the report with PENDING status and publishes IncidentReportedEvent.
  4. MS5 consumes the event and creates a WARNING alert targeted at OPERATOR.
  5. An administrator reviews the report and changes its status to RESOLVED or REJECTED.

C. Incident resolution and eco-points

  1. MS4 emits IncidentResolvedEvent when an incident is resolved (event referenced in MS1 design).
  2. MS1 consumes the event.
  3. MS1 creates a RewardHistory entry and increments the user's pointsBalance in one transaction.
  4. MS1 ignores duplicate events using eventId.

D. Route planning and collection

  1. Administrator selects a truck, driver, date and bins for a daily route.
  2. MS3 validates the driver through MS1 and retrieves bin coordinates through MS2.
  3. MS3 requests distance and duration from an external routing API; if unavailable, it uses a straight-line estimate and marks estimated=true.
  4. MS3 stores the route and ordered stops.
  5. Driver views the assigned route and updates route/stop status.
  6. When the route is completed, MS3 publishes RouteCompletedEvent; MS2 consumes it and resets fill levels for collected bins.

CHAPTER 18

Conclusion

SmartWaste proposes a microservices-based platform that connects real-time bin information, collection planning, citizen incident reporting, rewards and role-targeted alerts. Clear service ownership and separate databases support independent responsibilities, while REST/OpenFeign and RabbitMQ provide synchronous validation and asynchronous event propagation.

The design is sufficiently detailed to describe the platform boundaries, principal entities, core API contracts and key event flows. Before implementation or formal acceptance, the team should resolve the consistency items in Section 16 and complete the missing operational specifications.
